一、项目使命与价值
────────────────────────────────────────

2. 大厂同款：gRPC / FastAPI / Redis / Docker Compose 均为主流生产栈。
3. 学习跳板：每节附 *Learning Notes*，帮助你把概念映射到真实代码。

四、核心概念速查
────────────────────────────────────────
• gRPC：Google 开源的高性能 RPC 框架，支持双向流。
• ProtoBuf：二进制序列化格式，gRPC 的数据载体。
• FastAPI：基于 ASGI 的现代 Web 框架，自带类型校验与文档。
• Redis：内存 KV 数据库；本项目用 Hash 做原子计数器。
• Docker Compose：一条命令拉起多容器，确保环境一致。

────────────────────────────────────────
五、代码逐文件精解
────────────────────────────────────────
1. proto/telemetry.proto
   • 作用：定义数据契约。任何语言都需按此格式打包数据。
   • 关键片段：
     ```protobuf
     message Packet { string device_id=1; int64 timestamp=2; bytes payload=3; }
     service TelemetryIngest { rpc StreamPackets(stream Packet) returns(Ack); }
     ```
   • Learning Notes：字段编号用于版本兼容；`stream` 代表长连接可不断推送。

2. app/ingest.py（gRPC 服务器）
   • 作用：异步接收无限流数据 → Redis 自增计数。
   • 精华代码：
     ```python
     async for pkt in request_iterator:
         r.hincrby('device_metrics', pkt.device_id, 1)
     ```
   • Learning Notes：
     - `async for` + `grpc.aio` = 单线程也能万级 QPS；
     - Redis 哈希原子自增，天然多进程安全；
     - 出错时应 `context.abort(grpc.StatusCode.UNAVAILABLE, 'redis down')`。
   • 工程价值：在微服务或 IoT 场景里承担“数据入口聚合器”。

3. app/main.py（FastAPI Web 层）
   • 作用：HTTP API，把 Redis 里的计数转换为 JSON 返回。
   • 精华代码：
     ```python
     raw = r.hgetall('device_metrics')
     return [{"device_id":k.decode(),"count":int(v)} for k,v in raw.items()]
     ```
   
   • Learning Notes：
     - FastAPI 自动生成 `/docs` Swagger，非常友好；
     - `uvicorn --reload` 开启热重载，改代码秒生效。
   • 工程价值：给前端或第三方系统一个“随用随拿”的实时接口。

4. send_once.py（数据模拟器）
   • 作用：批量发送随机数据，压测 & 回归测试两用。
   • 用法：`python send_once.py --n 10000`（自定义数量）。
   • Learning Notes：
     - `grpc.insecure_channel('localhost:50051')` 直连本机 gRPC；
     - 生成三种 payload（JSON / binary / text），覆盖不同场景。

5. docker-compose.yml
   • 精华段落：
     ```yaml
     services:
       redis:
         image: redis:7-alpine
       realtime-demo:
         build: .
         environment:
           - REDIS_HOST=redis
     ```
   • Learning Notes：容器名即 DNS，Python 端 `os.getenv('REDIS_HOST','localhost')` 自动切换。

6. Dockerfile（多阶段）
   • 阶段 1 builder：`poetry install` + `protoc` 生成代码；
   • 阶段 2 runtime：仅复制 `/usr/local`，镜像 ~60 MB。

六、常见疑问 FAQ（纯文本版）
────────────────────────────────────────
- gRPC 连接失败（UNAVAILABLE:50051）
  检查：容器是否在跑；端口是否被占；防火墙。解决：`docker compose restart`。
- Redis 连接拒绝
  检查：`docker ps` 是否有 redis；6379 是否被占。解决：单独 `docker compose up -d redis`。
- /metrics 返回空
  先跑 `send_once.py` 注入数据；或看 ingest 日志有无 Redis 错误。

九、从 0 开始的实战路线图
────────────────────────────────────────
Step-1  初始化仓库
   • git clone 本项目
   • poetry install （本地调试）
   思考流程:
     1) 为什么选 Poetry 而不是 pip? —— 依赖锁定、防止‘在我机子能跑’。
     2) clone 后第一件事应该检查什么? —— `git status` 确认干净、`poetry check` 确认依赖OK。
     3) 常见错误: Python 版本不符。解决: `pyenv local 3.12` 或修改 `pyproject.toml`。

Step-2  定义数据契约
   • 编辑 proto/telemetry.proto
   • 运行 `make proto` 或 `python -m grpc_tools.protoc ...` 生成 *_pb2.py
   思考流程:
     1) 为什么先写协议而不是代码? —— 明确接口契约可避免后期返工。
     2) 字段编号如何设计? —— 预留跳号空间(10,20…)方便后续添加。
     3) 常见错误: 生成路径错导致 import error。解决: 加 `option python_package` 或调整 PYTHONPATH。

Step-3  编写摄取层 ingest.py
   • 创建 TelemetryServicer
   • 在 StreamPackets 中调用 Redis.hincrby
   思考流程:
     1) 先写最小可运行骨架(仅日志) → grpcurl 测试连通性。
     2) 再接入 Redis，自增前先写 `ping` 健康检查。
     3) 性能瓶颈思考: 网络IO > CPU，因此关注连接池、批量写。

Step-4  本地单进程调试
   • `python -m app.ingest` 监听 50051
   • 用 grpcurl 或 send_once.py 发送 1 条数据包
   思考流程:
     1) 观察日志有没有 `🚚 gRPC ingest`，没有则端口被占。
     2) grpcurl 如果超时，先用 `telnet 50051` 验证网络再看证书。
     3) Redis 计数不变? —— 检查 key space, 可能 device_id 空串。

Step-5  编写查询层 main.py
   • FastAPI `/metrics` 直接 hgetall Redis
   • `uvicorn app.main:app --reload` 查看 JSON 输出
   思考流程:
     1) 为什么直接读 Redis 而不是内存? —— 多实例一致性。
     2) JSON 序列化大对象的性能? —— 可 lazy 分页, StreamingResponse。
     3) 错误码设计: Redis down 应返回 503, 前端重试。

Step-6  容器化
   • 写 Dockerfile 多阶段；第一阶段安装依赖 + 生成 proto
   • docker build 测试镜像能跑 ingest/main
   思考流程:
     1) 分层顺序: 先复制 toml → 安装依赖 → 再复制源码, 以利用缓存。
     2) 架构兼容: slim 镜像缺 gcc? 需 `apt-get build-essential`。
     3) 镜像过大? —— 生产阶段仅复制 `/usr/local` reduce to 60MB。

Step-7  Compose 编排
   • docker-compose.yml 定义 redis + realtime-demo 两服务
   • 环境变量 `REDIS_HOST=redis` 注入应用容器
   • `docker compose up -d` 一键运行
   思考流程:
     1) 服务健康顺序: ingest 依赖 redis, 用 `depends_on` 或启动重试。
     2) 端口冲突: 本机已有 Redis? 改成 `6379:6379` 映射或不映射。
     3) 日志聚合: `docker compose logs -f` 观察两服务交互。

Step-8  编写数据模拟器 send_once.py
   • 使用 grpc stub 流式推送 1w 条随机数据
   思考流程:
     1) 压测目标: 找到 ingest QPS 上限, 先单线程再多进程。
     2) 数据多样性: 3 种 payload 检验序列化、大小 MTU 问题。

Step-9  性能压测
   • time python send_once.py --n 100000
   • 观察容器 CPU、网络、Redis hit/miss
   思考流程:
     1) CPU 升高=Proto 序列化瓶颈, 可改为 bytes payload.
     2) Redis 单核 110K ops/s 上限, 超时需集群或 sharding。
     3) 记录 p99 延迟, 不只看平均值。

Step-10  可观测 & CI
   • 加 Prometheus 指标、Grafana 看板
   • GitHub Actions build+pytest+docker push
   思考流程:
     1) 选择指标: ingest QPS, Redis ops, HTTP_latency.
     2) CI 失败三板斧: `docker buildx prune` 清缓存, `pip index` 换源, 重跑。

十、源码 API 速查与学习注解
────────────────────────────────────────
★ app.ingest.TelemetryServicer.StreamPackets(request_iterator, context)
  目的 : 异步消费客户端数据流并计数
  用法 : 由 gRPC 框架自动调用
  返回 : Ack(ok=True)
  工程意义 : 数据入口 + 快速确认，无需等待批处理

★ app.ingest.serve()
  目的 : 启动 gRPC 服务器并阻塞直至退出
  用法 : `python -m app.ingest` 或容器 CMD

★ app.main.metrics()
  目的 : HTTP GET `/metrics` 返回实时计数
  用法 : 浏览器 / curl / Ajax 定时拉取
  实际意义 : 可嵌入监控大盘或提供第三方接口

★ send_once.generate_sensor_data() / generate_binary_data() / generate_text_data()
  目的 : 构造不同类型 payload , 模拟 IoT 真实环境
  用法 : 内部被 generate_random_payload() 调用

★ send_once.gen_packets(n:int)
  目的 : 生成 n 个 Packet 对象的生成器
  用法 : stub.StreamPackets(gen_packets(10000))

★ app.pipeline.aggregator()
  目的 : (演示代码) 队列消费者—按内存字典计数
  用法 : main.startup 事件中 create_task 启动 (已被 Redis 方案取代)

★ app.pipeline.get_metrics_snapshot()
  目的 : 返回当前内存计数字典的浅拷贝

阅读顺序建议 : 先看 proto → ingest → send_once (双视角理解 gRPC) → main → Docker / Compose 。

疑问解答
@https://python-poetry.org/docs/basic-usage/ 
这个上面为什么写的是.toml
你要写的是.proto?
———————————————————————————————————————————————————————
两个完全不同的文件体系：
1) pyproject.toml
作用：给 Poetry／PDM／pip 等 Python 构建工具 看的，用来描述包名、版本、依赖。
放在项目根目录，由 Poetry 自动读取和写入。
后缀 .toml 是 配置文件格式（Tom’s Obvious Minimal Language）。
2) *.proto
作用：给 Protocol Buffers / gRPC 使用，描述跨语言的数据结构和 RPC 接口。
放在 proto/ 目录，之后用 protoc 生成 *_pb2.py、*_pb2_grpc.py 等代码。
后缀 .proto 是 IDL 文件，跟 .toml 没任何关联。
所以：
你在查 Poetry 文档时，看到的是 pyproject.toml——它告诉 Poetry “我要用哪些依赖（如 grpcio、redis）”。
你在写 gRPC 接口时，需要编辑 telemetry.proto——它告诉客户端/服务端 “Packet 有哪些字段，RPC 叫什么”。
二者一个管理 项目依赖，一个定义 网络协议，功能完全不同，只是都出现在同一个仓库里而已。
